# Orion-Client Build and Deployment

## 1. Purpose and Scope
Orion-Client is the on-device C++17 validation daemon. It uses CMake/Ninja, connects to Orion-HAL through the sibling source tree, and provides native and ARM64 Docker build paths. This guide documents the repository Makefile, its CMake targets, the `docker/` image, and the sample runtime/service surfaces. It does not claim hardware-in-the-loop validation.

## 2. Prerequisites
- Linux with GNU Make, CMake, Ninja, a C++17 compiler, and `ctest`.
- Protobuf/gRPC, SQLite, TOML, and other dependencies expected by the CMake configuration.
- A sibling `Orion-HAL` directory when using the repository's Docker mount layout.
- Docker with Buildx for ARM64 builds; QEMU/binfmt support may be needed on non-ARM hosts.
- `sshpass`, SSH/SCP access, and a reachable target for `deploy-a`, `deploy-b`, `run-a`, or `run-b`.

## 3. Setup
From this repository root, inspect available targets with `make help`. The Makefile keeps native output in `build/native` and cross output in `build/cross`. Docker image setup is automatic through `make docker-image`; `make docker-install` may invoke `sudo apt` when Docker is absent.

## 4. Build and Compile
```bash
make configure
make build
make docker-configure
make docker-build
```
`make build` configures with `cmake -GNinja -DBUILD_TESTS=ON` and builds with `ninja`. The Docker path builds the `orion` ARM64 image and runs the same CMake/Ninja flow under QEMU. Override parallelism with `make JOBS=N`; Docker caps its own jobs for emulation stability.

## 5. Test and Lint
```bash
make test
make docker-test
make format
make cppcheck
make doc
```
Native `make test` runs CTest filtered to `serializer_tests` and `runner_tests`; Docker runs all discovered CTest tests. `format` requires the generated Ninja `format` target and `cmake-format`; `cppcheck` requires its executable; `doc` requires the Ninja Doxygen target and Doxygen. These checks do not replace device testing.

## 6. Packaging and Artifacts
This Makefile does not define a packaging target. Build outputs are under `build/native/bin`, `build/native/lib`, or the corresponding `build/cross` directories. `make list` prints available native and cross applications. Documentation is generated by `make doc` into the CMake/Doxygen output location.

## 7. Deploy, Install, and Run
```bash
make deploy-a IP_A=192.168.1.3 HAL_SSH_USER=root HAL_SSH_PASS='<target-password>'
make deploy-b IP_B=192.168.1.13 HAL_SSH_USER=root HAL_SSH_PASS='<target-password>'
make deploy
make run-a
make run-b
make run APP_NAME arg1
```
`deploy` copies cross `lib/` and `bin/` to `/tmp/acu-test` on both configured targets. `run` executes native applications with `LD_LIBRARY_PATH=build/native/lib`; `run-a` and `run-b` deploy first and execute remote applications. The remote targets, username, and password are defaults only: provide real values through Make overrides or environment-aware shell handling, and do not commit credentials. The `systemd/` unit and `conf/client.conf.sample` still require target-specific installation and configuration.

## 8. Cleanup
```bash
make clean
make docker-clean
make docker-shell
```
`make clean` removes both build trees. `docker-clean` removes the cross build directory inside the image; `docker-shell` opens an ARM64 development shell. `make docker-image` and `make docker-install` are prerequisites for Docker cleanup/shell operations.

## 9. Hardware, Cloud, and Manual Verification Caveats
The adapter code and CTest coverage are not hardware-in-the-loop evidence. Verify gRPC connectivity, local HalService behavior, SQLite WAL spooling, log collection, permissions, systemd startup, and each real HAL module on an actual target. Deployment uses direct SSH/SCP and no cloud service; it requires network reachability and target credentials. Remote `run` intentionally tolerates failures when running all applications, so inspect target logs and results manually.
